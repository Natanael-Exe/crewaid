**TanStack AI versus AI SDK for Crewaid, 3 October 2026**

Research snapshot: the review below records the analysis before board changes. The subsequent implementation plan is [the D-158 modernization handoff](../plans/ARCHITECTURE-MODERNIZATION-2026-10-03.md); no product migration is implemented by this report. The user subsequently confirmed there are no launched users or production data; D-158 now omits historical data/client compatibility and deployment rollback work.

**I support a staged TanStack AI migration when the goal includes replacing Crewaid’s custom chat plumbing.** Native AG-UI, typed tool/interrupt UI, persisted approvals, provider-independent lazy discovery, and context-compaction middleware are useful together. They could remove more maintenance than changing the model loop alone. This revises the earlier recommendation to retain AI SDK: the stronger case is an integrated backend/frontend simplification, with local PostgreSQL ownership and the current shared-computer model preserved.

AG-UI itself does not require TanStack. It is a communication protocol between an agent backend and its UI. AI SDK can be translated into it. However, a ready-to-use, version-compatible bridge should not be assumed: the public npm lookup for `@ag-ui/vercel-ai-sdk` returned 404, while the inspected upstream adapter source declares `ai: ^4.3.16`. Crewaid runs AI SDK 7. CopilotKit offers a separate integration route, but its OpenDots-era runtime also brings its own SDK/protocol versions. Native TanStack is therefore a practical advantage over an unverified bridge. [AG-UI adapter manifest](https://github.com/ag-ui-protocol/ag-ui/blob/main/integrations/vercel-ai-sdk/typescript/package.json), [CopilotKit custom agents](https://docs.copilotkit.ai/angular/deepagents/backend/custom-agent).

**The comparison is grounded in current source and published packages.** Crewaid uses `ai@7.0.89`; npm reports `7.0.127` as latest at retrieval, a patch difference rather than an obsolete major. I inspected its bundled version-matched documentation and source. TanStack source was inspected at `b8bab43b98ac91e201dc1dae8a3811b348d34504`. I also downloaded published npm tarballs without installing or executing them and confirmed the relevant APIs are present:

The current sandbox package was also identified as 0.5.18; its documentation and source were reviewed for fit, rather than treated as a replacement for our desktop. Versions are retrieval snapshots and should be pinned as a compatible set if a migration is implemented. No application dependencies, endpoints, contracts, or task-board state were changed. No live provider or TanStack/Nest/Electron integration was run for this comparison.

**The biggest distinction is how much of the chat lifecycle each library packages for us.** Both already support streaming, model providers, tool execution, approvals, typed schemas, and configurable loops. Neither requires hosting on its publisher’s platform. The following table compares actual library surfaces with Crewaid’s current implementation, rather than treating an unused feature as an installed capability.

| Concern | AI SDK / current Crewaid | TanStack AI | Assessment for Crewaid |
| --- | --- | --- | --- |
| Wire protocol | AI SDK has its own UI stream; Crewaid instead projects core events into custom WS frames | Native AG-UI events and request handling | A meaningful standardization benefit. |
| React conversation state | AI SDK supplies `@ai-sdk/react`; Crewaid currently uses its own hook/reducer | `useChat`, typed parts, interrupts, headless rendering factory | Strong opportunity to remove generic chat state. Both libraries can help; TanStack combines this with native AG-UI. |
| Agent loop | `ToolLoopAgent`, custom stop conditions and callbacks | `chat()` with composable strategies/middleware; also reusable agent helpers | Mostly equivalent mechanics; no reason to rewrite solely for the loop. |
| Tool contracts | Zod-backed `tool()`, inferred tool/UI types | `toolDefinition()` with server/client implementations, output/approval schemas | Useful authoring ergonomics, subject to our shared-contract rules. |
| Tool approvals | SDK supports dynamic allow/deny/approval policy; Crewaid owns continuation and UI | Built-in approvals plus generic typed interrupt boundaries | Useful, but preserve our actual authorization policy. |
| Durable pending approvals | Current continuation includes process-local state | Persistence stores pending interrupts and validates later resume batches | Substantial fit for part of M9-BE-05. |
| Transcript persistence | Crewaid owns PostgreSQL writes, checkpoints, and hydration | Middleware and reconstruction over app-supplied stores, with a shipped Prisma adapter recipe | Strong fit for our existing Prisma/PostgreSQL stack; a thin store mapping replaces generic lifecycle wiring. |
| Stream reconnection | Custom Crewaid reconnect/resync logic; SDK offers transports/resume patterns | Ordered event-log adapter and automatic client reconnection, including WebSockets | Useful delivery-layer simplification; production needs a durable backend. |
| Context management | Crewaid uses SDK pruning plus its own budget/trim behavior | Dedicated provider-context compaction strategies and persistence-aware checkpoints | Good candidate for replacing trimming mechanics. |
| Large tool catalogs | Current portable two-tool MCP bridge and listing budget | Provider-independent `lazy: true` discovery and direct discovered tool calls | One of the strongest backend reasons to migrate. |
| MCP | Existing AI SDK MCP client and credential/ownership lifecycle | Managed discovery/lifecycle, manual typed clients, pooling, Apps/input features | Feature-rich alternative; current security and scoping cannot be discarded. |
| Providers | Dedicated OpenAI, Anthropic, OpenRouter and custom bindings | Adapters cover our provider families, including OpenAI-compatible endpoints | Check feature parity, not just provider names. |
| Billing/usage | SDK middleware reserves and settles included-model spend; explicit cache accounting | Per-iteration usage hooks, detailed usage/cost fields | Requires semantic normalization and metering porting. |
| Observability | Privacy-safe telemetry and Pino already exist | App-lifecycle middleware, devtools, OpenTelemetry integration | Easier extension; preserve redaction and cost truth. |
| Media/realtime | SDK has server APIs and additional integrations | Dedicated activities, client hooks, generation persistence | Attractive future feature breadth, not the main current migration payoff. |
| Computer ownership | Crewaid’s per-user computer and bot seats | Optional coding-harness sandbox packages | Keep our computer architecture. |
| Operational durability | Queues, persistent turn rows, unfinished restart/recovery work | Persistence/replay plus specialized durable harness runs | Helps several layers; does not make arbitrary external actions exactly once. |

Sources: [TanStack comparison](https://tanstack.com/ai/latest/docs/comparison/vercel-ai-sdk), [AI SDK transports](https://ai-sdk.dev/docs/ai-sdk-ui/transport), [TanStack React UI](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/ui/react.md), [middleware interface](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai/src/activities/chat/middleware/types.ts).

**The frontend is where an integrated migration could remove the most generic application code.** Crewaid’s `chatReducer.ts` and `useChat.ts` handle streamed messages, tool state, approvals, hydration, and reconnect behavior alongside product-specific state. TanStack supplies message-part assembly and interrupt state through `useChat`, with headless tool/part rendering through `createChatHook` in `@tanstack/ai-react/ui`. We supply the visible HeroUI components, styling, screen cards, and interaction copy. There is no requirement to adopt TanStack Start, Router, or a different backend framework. [Current reducer](../../apps/desktop/src/renderer/state/chatReducer.ts), [current hook](../../apps/desktop/src/renderer/state/useChat.ts), [headless React UI](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/ui/react.md).

This would replace the conversation slice of that state, not the complete reducer or WebSocket subsystem. Bot roster changes, Work updates, recordings, computer lifecycle, and noVNC binary frames remain application concerns. Measure the code removed after a real vertical slice. The alternative of retaining AI SDK and using its React hook would also eliminate some hand-built chat state, so compare against that stronger baseline, rather than assuming all current custom code is forced by AI SDK.

TanStack’s headless UI also makes CopilotKit optional. For Crewaid, I would first evaluate **TanStack backend plus TanStack React chat state, keeping HeroUI**. OpenDots uses a different combination: TanStack backend through CopilotKit, with CopilotKit React components. Installing both frontend state systems by default would add overlapping responsibilities.

**Prisma persistence is a direct fit, and should be part of the migration.** The user’s persistence example is accurate: `defineAIPersistence`, `defineMessageStore`, and `withPersistence` are present in the published `@tanstack/ai-persistence@0.7.2` tarball. That package also contains `skills/ai-persistence/build-prisma-adapter/SKILL.md`. TanStack accepts our own schema and database client; basic transcript persistence needs `loadThread` and `saveThread`. “Write an adapter” here means implementing these storage functions against Prisma, while reusing TanStack’s lifecycle and reconstruction behavior. It does not require another database, another ORM, or hosted transcript storage. [Adapter guide](https://tanstack.com/ai/latest/docs/persistence/build-your-own-adapter), [store contracts](https://tanstack.com/ai/latest/docs/persistence/store-reference).

For Crewaid, the proposed mapping is:

| TanStack concept | Existing Crewaid foundation | Integration work |
| --- | --- | --- |
| `threadId` | `Conversation.id`, already related to one bot | Resolve and authorize through the bot’s owner; retain topic boundaries and read state. |
| Message store | `Message` rows, including JSON `parts` | Convert old AI SDK parts and new TanStack model messages through a versioned boundary; preserve stable message identities, attachments, task/routine provenance, and references. |
| Run store | `AgentTurn` rows | Map run status, identifiers, timestamps, and normalized usage; retain step checkpoints and the active-turn fence. |
| Interrupt store | Existing approval policy plus process-local continuation state | Add durable pending/resolved approval records and transactional response consumption; reuse the current authorization policy. |

This is a fit assessment, not a completed adapter or an assumption that the representations are identical. Our `Message` rows carry product relationships that the small JSON-thread example does not model. `saveThread` supplies a full authoritative replacement, so its Prisma implementation must reconcile that message set transactionally while preserving those relationships, rather than blindly deleting and recreating rows. Run and interrupt records add capabilities beyond the two-function transcript minimum. [Crewaid schema](../../apps/orchestrator/prisma/schema.prisma#L385), [existing message storage](../../apps/orchestrator/src/messages/messages.service.ts#L43), [run schema](../../apps/orchestrator/prisma/schema.prisma#L473), [TanStack chat persistence](https://tanstack.com/ai/latest/docs/persistence/chat-persistence).

**Recommended persistence ownership: TanStack lifecycle → Prisma-backed stores → our PostgreSQL.** Use the package’s adapter conformance suite when implementing this mapping. Keep stream replay as its separate delivery layer; saving a completed transcript alone does not preserve an in-flight response. The Prisma recipe is implementation guidance, not a reason to duplicate our existing models or introduce a second transcript authority. [Adapter conformance guidance](https://tanstack.com/ai/latest/docs/persistence/build-your-own-adapter), [persistence and delivery boundaries](https://tanstack.com/ai/latest/docs/persistence/internals).

**Persisted interrupts are a material backend benefit.** With message, run, and interrupt stores, TanStack’s persistence middleware records pending decisions, restores them, validates resume entries against server-held records, and commits consumed responses at a success boundary. An adapter can implement `commitBatch` to make batch consumption atomic. This can replace some of our process-local approval orchestration while allowing a human to answer after restart. It still needs authenticated approvers, scoped records, action revision checks, and safe recovery when the tool itself has an uncertain outcome. [Chat persistence](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/persistence/chat-persistence.md), [resume implementation](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai-persistence/src/middleware.ts).

The simple approval tutorial also offers an ephemeral path rebuilt from client history. Crewaid should use the server-authoritative persisted path. The persistence merge behavior can replace messages with the same id and truncate a stored tail at a matching incoming id, supporting reload/edit workflows. Therefore, accepting arbitrary client history would be a product and trust change. Keep server-owned history and explicitly authorize supported edits, clears, and regeneration. Bare `threadId` strings do not enforce tenant isolation. [Persistence ownership and merge semantics](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/persistence/internals.md).

**Our automatic-review policy still needs to remain a first-class service.** TanStack’s basic tool `needsApproval` flag is boolean, whereas Crewaid already decides allow, deny, or ask using mode, effect, and rules. TanStack middleware can inspect proposed tool calls, skip execution with a result, or interrupt at a lifecycle boundary. That is an integration path for the existing policy, not a reason to replace it with a fixed flag. Edited approval arguments need fresh validation and authorization against the final action; client-declared tools and forwarded properties must not confer server capabilities. [Tool types](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai/src/types.ts), [middleware hooks](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai/src/activities/chat/middleware/types.ts), [approval decisions](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/interrupts/tool-approval.md), [Crewaid policy](../../apps/orchestrator/src/agent/auto-review.ts).

**Provider-independent lazy discovery could simplify our plugin bridge.** TanStack withholds lazy schemas, advertises a catalog, returns requested definitions through a synthetic discovery tool, and exposes those tools directly on later iterations. Prior discoveries can be recovered from history. This works at the SDK loop level, rather than requiring a particular provider’s native search feature. It could remove parts of Crewaid’s custom listing/call bridge and soften the pressure created by fixed estimated-token budgets. [Lazy discovery guide](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/tools/lazy-tool-discovery.md), [implementation](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai/src/activities/chat/tools/lazy-tool-manager.ts).

Discovery does not authorize execution. Construct the current tool set from the user’s current grants, prevent collisions across connected servers, and revalidate before executing. Test revoked tools against stale discovery history. Lazy loading can add an extra model iteration, and accumulated discoveries can grow context again; measure latency, token cost, and tool-selection quality before removing our portable fallback. Some dynamic MCP servers cannot provide compile-time literal tool types unless generated contracts are introduced; runtime schema validation remains essential.

**Compaction middleware is another good fit, with modest rather than revolutionary savings.** TanStack offers eviction, summarization, and clearing old tool results. It preserves tool/result pairing and writes a provider-only context view while keeping the canonical transcript intact. Crewaid already uses SDK pair-aware pruning, so this replaces surrounding mechanics and adds reusable strategies rather than fixing an absent feature. Preserve attachment semantics, signed reasoning, memory placement, approval context, and context-limit behavior. Summarization also has model cost and latency. [Compaction](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/advanced/compaction.md), [current trimming](../../apps/orchestrator/src/agent/turn-runner.ts#L909).

**There are three different recovery promises to evaluate.** A message store saves history and pending decisions. A resumable stream replays an ordered event log without rerunning the model. An execution recovery system continues or safely reconciles work after the process driving it disappears. TanStack documents these distinctions. In-process `memoryStream` is for one process; production requires an external log or custom durable adapter. Its replaying GET cannot restart a dead ordinary model-call producer automatically. [Resumable streams](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/resumable-streams/overview.md).

TanStack’s durable sandbox runs go further for supported coding harnesses: the child process writes a journal, a successor driver can attach, driver epochs fence stale log writers, and a reaper cleans up abandoned runs. That is real functionality relevant to V2-03, but it is specialized to an independently running harness. Our ordinary in-process browser-tool agent does not acquire the same recovery properties merely by switching `ToolLoopAgent` to `chat()`. Distributed locks and a scheduled reaper also remain deployment responsibilities. [Durable harness runs](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/sandbox/durable-runs.md), [takeover requirements](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/sandbox/takeover.md), [lock semantics](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/advanced/locks.md).

**Billing is a migration blocker until normalized usage is verified.** Our included-model middleware reserves spend before a provider call and settles success, failure, or partial cancellation. SDK replacement must preserve that admission/settlement behavior. Having an `onUsage` callback or provider-reported cost does not replace reservation or durable charging. Cache fields are supported in TanStack, but their aggregate meaning differs in the inspected Anthropic path.

For a simple raw Anthropic usage example with `input_tokens = 100`, `output_tokens = 20`, `cache_creation_input_tokens = 200`, and `cache_read_input_tokens = 300`:

| Normalization | Input quantity | Cache details | Consequence |
| --- | --- | --- | --- |
| Installed AI SDK Anthropic adapter | Total input = 600, non-cache input = 100 | Write = 200, read = 300 | Current Crewaid input-token accounting includes cache tokens. |
| Inspected TanStack Anthropic builder | `promptTokens` = 100; its simple total = 120 | Write = 200, cached = 300 | Renaming `promptTokens` to `inputTokens` would undercount context and alter cost calculations. |

These values are a source-derived arithmetic example, not a live provider measurement. Normalize raw semantics into Crewaid’s established usage contract and keep unknown usage distinct from measured zero. Repeat fixtures for OpenAI, Anthropic, OpenRouter, cache use, reasoning, aborts, retries, and a response lost after spend settlement. [TanStack Anthropic usage builder](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai-anthropic/src/usage.ts), [installed AI SDK usage conversion](https://unpkg.com/@ai-sdk/anthropic@4.0.47/src/convert-anthropic-usage.ts), [Crewaid included-model metering](../../apps/orchestrator/src/billing/included-models.service.ts).

**The provider abstraction is a wider migration than one agent function.** AI SDK types appear in model resolution, error normalization, skills compilation/revision, memory distillation, tool binding, billing middleware, telemetry, transcript history, and tests. The existing execution seam keeps model credentials out of requests but still carries SDK `ModelMessage` and `ToolSet` representations. It is helpful, not completely SDK-neutral. [Execution port](../../apps/orchestrator/src/agent/execution/execution-backend.port.ts), [provider factory](../../apps/orchestrator/src/models/provider-factory.ts).

Keep ownership-scoped adapter construction, credential encryption, custom-endpoint guarded fetch, error redaction, prompt-cache ordering, and current model capabilities. TanStack supports explicit keys and provider client configuration; avoid copying browser-key BYOK examples into our backend. Crewaid needs background bots and routines to work without a connected client, so encrypted server-side credentials remain appropriate. Per-model compile-time narrowing is most useful for fixed literal models; customer-selected dynamic catalogs still need runtime capability checks. Preserve stored history through a versioned conversion boundary rather than silently interpreting old AI SDK parts as TanStack parts. [Explicit provider construction](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai-openai/src/utils/client.ts), [TanStack browser BYOK design](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/advanced/byok.md).

Isomorphic definitions also need to respect `packages/shared`’s Zod-only dependency rule. Keep neutral schemas there and derive SDK-specific server/client definitions in appropriate integration code, unless a deliberate contract decision changes that rule. Do not put provider SDKs, credentials, or server execution into the Electron renderer to gain type inference.

**The comparison page is useful, but several entries need qualification.** It openly states that it is written from TanStack’s perspective. Its native AG-UI and persistence claims have concrete implementation behind them. Some contrasts overstate AI SDK’s limitations:

- AI SDK works outside Vercel and can use direct provider packages without AI Gateway.
- Its custom stop conditions already support business rules and token limits; Crewaid uses this today.
- AI SDK has React tool state, typed messages, approvals, and custom transports, including WebSocket integration surfaces. Crewaid has not adopted its React hook.
- The page’s “Anthropic-only” native tool-search claim does not match the installed OpenAI adapter, which exports `toolSearch` and deferred-loading support. TanStack still has an advantage in provider-independent discovery.
- AI SDK 7 includes MCP Apps host helpers and a React renderer; interactive MCP UI is not exclusive to TanStack.
- App-level middleware is an ergonomic distinction, rather than proof AI SDK lacks per-call telemetry, tool policy, or lifecycle hooks.

Evidence: [AI SDK transport documentation](https://ai-sdk.dev/docs/ai-sdk-ui/transport), [installed tool approvals](https://unpkg.com/ai@7.0.89/docs/03-agents/06-tool-approvals.mdx), [installed OpenAI search tool](https://unpkg.com/@ai-sdk/openai@4.0.55/src/tool/tool-search.ts), [installed MCP Apps documentation](https://unpkg.com/ai@7.0.89/docs/03-ai-sdk-core/17-mcp-apps.mdx).

**OpenDots validates one integration combination, not the entire current TanStack ecosystem.** Its lockfile resolves `@tanstack/ai@0.63.0`, `@tanstack/ai-openai@0.25.1`, and `@ag-ui/core@0.0.59`. The inspected current TanStack 0.64.0 package depends on AG-UI core 1.0.0. OpenDots wraps its TanStack factory in CopilotKit `BuiltInAgent`, uses CopilotKit React on the frontend, and delegates persistent conversations to Intelligence. It does not demonstrate a native TanStack React frontend, our PostgreSQL adapter, or the proposed persisted-approval workflow. [OpenDots lockfile](https://github.com/CopilotKit/OpenDots/blob/c2569bb6a13a22e565cf3eb791c62267d06babb1/package-lock.json), [agent factory](https://github.com/CopilotKit/OpenDots/blob/c2569bb6a13a22e565cf3eb791c62267d06babb1/src/server/dot-agent.ts), [current TanStack manifest](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/packages/ai/package.json).

Compatible protocol versions and extension behavior need an interoperability test. Standard events can render in another AG-UI client, but TanStack-specific custom events, typed structured output, interrupts, and continuation semantics may need client support. A shared protocol name does not guarantee every UI implements every extension. Current packages are pre-1.0, and their migration guides document breaking changes; version pins and upgrade checks matter. [Custom events](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/protocol/custom-events.md), [migration history](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/migration/migration.md).

**Switching SDKs does not require changing the shared computer.** Keep one computer per user, per-bot X display/Chrome/private workspace, named login leases, and noVNC. TanStack is the orchestration/communication layer; browser tools can call our existing computer service. Its sandbox helpers primarily target coding-agent processes and workspace lifecycles. A default lifecycle that destroys a sandbox after a run would conflict with our persistent logged-in computer. Evaluate harness support separately under V2-03, with our ownership and persistence boundaries retained. [Sandbox scope](https://github.com/TanStack/ai/blob/b8bab43b98ac91e201dc1dae8a3811b348d34504/docs/sandbox/overview.md).

**I would migrate in stages with a measurable deletion goal.**

| Stage | Scope | Required evidence before expanding |
| --- | --- | --- |
| 1 | One backend execution path using TanStack; preserve current product contracts initially | Provider binding, instructions, one read tool, one write approval, cancellation, limits, and normalized usage match expectations. |
| 2 | One conversation rendered with TanStack React and native AG-UI | Text/reasoning/tool state, approval, reconnect, concurrent bots, and existing HeroUI interaction work; generic state code is actually removed. |
| 3 | PostgreSQL message/run/interrupt stores and a production stream-log adapter | Approval survives process restart; resume batches are authorized and atomic; stale workers and duplicate requests cannot overwrite current state. |
| 4 | Lazy MCP discovery and compaction | Revocation, collisions, credentials, approval policy, token budget, pair-safe trimming, attachments, and history remain correct. |
| 5 | Skills, memory/model calls, metering, and error paths | All remaining SDK consumers have parity; old history remains readable and runnable. |
| 6 | Remove obsolete AI SDK adapters, generic chat reducers, and duplicated plumbing | One authoritative execution/message path remains; retained custom code has a product-specific reason. |

Use the existing regression scenarios rather than a second permanent orchestration framework. Temporary dual backends are useful for comparison, but avoid indefinitely maintaining two loops or two transcript authorities. SDK-neutral execution/history/tool representations become justified during this migration because two concrete implementations now inform the abstraction.

The protocol/contract changes must be documented before implementation, including how current WS events, stored message parts, and approval identifiers map to AG-UI. Keep screen transport and product notifications separate. In particular, preserve background routine execution, bot-message chain budgets, Work’s user/bot-controlled semantics, and login-profile exclusivity.

**The recommendation is conditional on demonstrated simplification, rather than feature count.** TanStack is a credible direction for Crewaid’s backend and frontend together. Its most relevant gains are the standard wire protocol, persisted interrupt lifecycle, lazy tools, and reusable UI state. Keep PostgreSQL, NestJS, Better Auth, BullMQ, HeroUI, and the shared computer. Finish browser targeting, enforced human takeover, external-action authorization, and launch recovery independently of the SDK choice. A successful migration removes generic code while retaining those boundaries; changing the SDK without removing that plumbing would deliver much less value.
